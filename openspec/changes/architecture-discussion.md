# 架構調整討論 v3：全域設定雲端同步 (Google Sheets)

## 討論進度更新
我們確認了僅依靠單一姓名顯示（I1 儲存格）無法解決「名單順序不一、推算基準不一」的問題。因此，V3 方案將採用「全量配置 JSON 封包」同步機制。

## 建議方案：全量配置 JSON 同步 (Full JSON Config Sync)
為了達成「一人修改、全體對齊」，我們需要同步的不職是結果，而是**整個系統的設定模型**。

### 1. 核心技術細節：JSON 設定大包
我們將定義一個「設定封包 (Config Blob)」，內容包含：
- **人員主檔 (`staff`)**：全體人員名單、是否有參與輪班、性別等基礎資訊。
- **區域設定 (`areas`)**：區域清單、優先級、人數上限。
- **輪值狀態 (`plannerRotation`)**：
    - **人員 ID 順序清單 (`planners`)**：定義誰接在誰後面的「關鍵順序」。
    - **推算基準日 (`baseDate`)**：定義這套順序是從哪天開始算的標記。
    - **推算基準序號 (`baseIndex`)**：定義基準日當天排到的人是誰。

### 2. 資料儲存與存取流程
- **儲存位置**：Google Sheets 的 `[Schedule]` 工作表 **J1 儲存格**。
    - *安全性：原有 APK 或舊系統讀取 A:I 欄，完全看不到 J1，因此不會造成任何崩潰或資料錯位。*
- **寫入流程 (Admin -> Cloud)**：
    - 當管理員在後台修改人員、調整區域或按下「推進下一週」時，瀏覽器會將最新的「設定大包」轉換為 JSON 字串，透過 API 存入 `J1`。
- **讀取流程 (Cloud -> All Users)**：
    - 任何人開啟或重新整理網頁時，程式會先呼叫 GAS 的 `?type=config`。
    - 取得 `J1` 內的 JSON 大包後，立即**蓋過**本地的 `localStorage`。
    - **結果**：所有人電腦裡的「名單順序」與「基準日」都被強迫對齊，程式算出來的「下一週負責人」就會一模一樣。

### 3. 改版優勢
- **極低風險**：採用「外掛式資料」存取，原有讀取 APK 的位置讀不到新增的資料欄，架構不變，只是資料儲存位置從靜態檔案變成了雲端欄位。
